# rrk-scraper: handoff brief

## Goal and rules
Scrape the public "open data" listing of rrk.ir (Iranian official-gazette company ads) into `rrk.db`, and explore it in the local GUI.
The site is Oracle APEX 23.1 (app 200, page 199) behind ORDS with friendly URLs. Only that public page is in scope.
Keep requests few and slow. Never commit or paste session captures: `*.har`, `*.html`, `*.log`, `debug/`, `ads.json`, `rrk.db` (all git-ignored). HAR files hold live cookies, so never repeat cookie values.

Run everything from `src/rrk` (imports are top-level: `apex`, `rrs`, `parsing`, `models`). Setup: `pip install -e '.[test]'` from the repo root (a venv: this machine's system Python has no pytest, and only `python3`). Tests: `python3 -m pytest` from the repo root (`tests/conftest.py` sets the path); tests that need a capture or `tests/labelled/` skip without it.

## How the site works (verified live and from browser HARs)
1. `GET /ords/r/rrs/rrs-front/home` creates the session: it sets cookies `ORA_WWV_APP_200` (APEX) and `cookiesession1` (firewall, probably Fortinet) and redirects to `home?clear=1&session=<id>`. No login: the APEX user is `nobody`.
2. The home page links to the data page `داده-باز?clear=199&session=<id>&cs=<checksum>`. The `cs` is required, so take the link from the page.
3. The search is a page submit: `POST /ords/wwv_flow.accept?p_context=rrs-front/داده-باز/<session>` with `p_request=btnSearch`, all 51 page items in DOM order (3 carry a `ck` checksum), `salt`, `protected`, `p_page_submission_id`. The answer is `{"redirectURL": ...}`.
4. The redirected results page holds the Interactive Grid `AGAHI_GHANOUNI2` (region `1083730177584955508`, report `1115937865841778825`). Its `ajaxIdentifier`, the tail of `ajaxColumns`, `salt` and `protected` are re-signed on every page load.
5. Rows come from `POST /ords/wwv_flow.ajax?p_context=...` with `fetchData {firstRow, maxRows: 100}` (the browser picks 100 itself; the user only chooses `P199_NOE_AGAHI=12`). The answer is `regions[0].fetchedData {values (16 cells/row), firstRow, moreData, totalRows}`. Type 12 has 554 rows.
- `<base href="/ords/">`: resolve form and AJAX URLs against it. The server sends `Referrer-Policy: strict-origin`, so the browser's Referer is always `https://rrk.ir/`.
- The browser also runs small page-load dynamic-action calls (`P0_SEARCH_ITEM`, `P199_FOOTER*`, `P199_SINGLE_SEARCH*`, about 0.25 s each). They start after the grid request, so they are not prerequisites.
- `FOOTER_H` in the listing is cut to 200 characters. The full text is on `f-detail-ad?p28_code=...` (the links carry `cs`). Not fetched yet.

## Design of the next steps
Put new code in the existing stubs, not beside them.

**1. Storage**
Built: see the code layout. Every run re-reads the whole listing (6 pages, about 4 min) and upserts it; rows not seen again keep their old `last_seen`. All 554 type-12 rows have a `detail_code`; rows without one would be skipped with a warning.
- `models/issuer.py` holds the registration office (decided 2026-10-31), see the code layout.

**2. Detail pages**
- Tested live by the user (2026-10-29): page 28 enforces `cs`. A link without a valid `cs` for the session gets an APEX error page, and the firewall reacts too ("firewall-ish" page). Never build detail URLs from the code alone, and never reuse a link in another session.
- Built: `scrape_listing()` returns the `detail_code → link` map of the session; only listed codes are fetched. Worker threads each use `ApexSession.fork()`: a tab sharing the cookie jar (like browser tabs), with its own connection and TCP keepalive. The main thread does all database writes.
- Bad requests trip the firewall, so stop the whole run at the first error or firewall page instead of retrying it.
- Pacing: `config.WORKERS` (1, `--workers 3` tested) and `DETAIL_DELAY` (3 s per worker). The total rate is what matters to the site.
- Confirmed live: 3 workers in the same session get through, and APEX doesn't mix up their pages.
- Content: `P28_TEXT` (labelled ad text) only holds a payment notice; the real full text is the "متن آگهی:" region. The page's other fields repeat the listing row, so only the new ones are stored. The page itself is never stored (only `--debug` archives it).
- Open: how long an APEX session lives. If it expires during the detail run, list again to get fresh links.

**3. Other ad types**
- Built: the dropdown call runs every run and upserts `ad_types` (`last_seen` older than the run = dropped from the list). Unknown codes in `--type` stop the run.
- Concurrency: one `RRSClient` (own session) per type, `--types-at-once N`. Never two searches in one session: the search writes `P199_NOE_AGAHI` into session state and the detail links are tied to that session. With `--debug` each type archives to `debug/<time>/type-<code>/`.
- Speed (type 9, 2026-10-29): details at 64 workers keep up with the listing (~750-850 pages/min; bursts of `RemoteDisconnected`, all absorbed by retries), so the listing is the bottleneck. Grid pages stay at 100 rows like the browser (the user rules out bigger pages); the listing is sped up with several sessions per type instead.

**4. Recovery and retry**
- The database is the checkpoint. A new run fetches whatever is still missing. Detail links die with their session, so `--missing-only` re-lists only the dates of the missing ads (`gap_windows`); `--detail-backlog` keeps that gap small in the first place.
- Built, HTTP level (`apex/session.py`): `ConnectionError` (incl. `RemoteDisconnected`, the user's most common failure) and timeouts are retried after `RETRY_WAITS` (2, 15, 60 s) on a new connection; connect timeout 15 s. A page submit (`wwv_flow.accept`) is only retried when it never left (`ConnectTimeout`).
- Built, type level (`scraper/pipeline.scrape_type`): a network error that outlasts those retries, or an unreadable grid answer (`ListingParseError`: session ended), reruns the type in a fresh session (`config.TYPE_ATTEMPTS` 3, `SESSION_RETRY_WAIT` 60 s). It lists again, because the links are session-bound, and fetches only the missing details. `DetailPageError` (firewall or APEX error page) is never retried; its message now carries the page `<title>`, to learn what an expired session looks like.
- Detail failures: only a wrong page (`DetailPageError`) increases `attempts` and saves `last_error`; a network error doesn't count against the ad, nor does a fetch cancelled because its session stopped. When one worker fails, the pages the others already fetched are still saved. Codes past `MAX_ATTEMPTS` are skipped, and every run ends by logging how many and why (`repository.given_up_details`).
- Run level (`main.py`): a type that fails on the network after its fresh sessions ends alone; the other types go on. Only a `DetailPageError` stops new types from starting (the firewall may be reacting). This came from the 2026-10-29 run (`--type all --types-at-once 3 --workers 6`): after ~35 min two `RemoteDisconnected` errors (types 3 and 2) cancelled the 11 types still queued.
